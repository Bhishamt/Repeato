# Deployment

## The honest starting point

This build runs on SQLite through `better-sqlite3`. That is a native module with a synchronous,
single-writer model and it needs a persistent filesystem. **Vercel Functions do not provide one.**
So the repository as it stands deploys cleanly to a single Node host (a VPS, Fly.io, Railway, a
container), but not to Vercel as-is.

The Postgres/Supabase schema and RLS policies are written (`supabase/migrations/`). What is missing
for serverless is the adapter: `lib/db.ts` and the call sites in `lib/services.ts` speak
`better-sqlite3`'s synchronous API. `lib/services.ts` is the only module that issues SQL, so the
port is one file plus `lib/db.ts` — not a rewrite of the app.

## Option A — single Node host (works today)

```bash
npm ci
npm run seed        # optional; skip in production and create the admin explicitly
npm run build
npm start           # serves on :3000
```

Requirements:

- Node 20+ (built and tested on Node 24).
- A persistent volume mounted at the path in `DATABASE_PATH` (default `./data/repeato.db`).
- `NODE_ENV=production` so the session cookie is `Secure` — therefore HTTPS termination in front.
- `APP_URL` set to the public origin; it is used for QR payloads and metadata.
- One process. SQLite with WAL handles concurrent readers and one writer; running several replicas
  against the same file over NFS will corrupt it.

Backups: copy the database file while the app is stopped, or use `sqlite3 data/repeato.db ".backup
backup.db"` online. The ledger is append-only, so point-in-time recovery matters more than schema
migration.

## Option B — Vercel + Supabase (the target architecture)

Steps, in order:

1. **Create the Supabase project.** Note the project URL and the publishable (anon) key; keep the
   secret/service key server-side only.
2. **Apply migrations.**
   ```bash
   supabase link --project-ref <ref>
   supabase db push          # runs supabase/migrations/0001_init.sql, 0002_rls.sql
   ```
   `0001` creates the enums, tables, indexes and the `account_balances` view. `0002` enables RLS on
   every table and adds deny-by-default policies.
3. **Port the adapter.** Replace `better-sqlite3` usage in `lib/db.ts` with a Postgres client
   (`postgres` or `@supabase/supabase-js` with the service key), and convert the synchronous calls
   in `lib/services.ts` to `await`. Transactions become `BEGIN … COMMIT` blocks or a Postgres
   function; `BEGIN IMMEDIATE` maps to a normal transaction with `SELECT … FOR UPDATE` on the reward
   row for the stock check. `INSERT OR IGNORE` becomes `ON CONFLICT DO NOTHING`. `datetime('now')`
   becomes `now()`.
4. **Map auth.** Either keep the existing session table (Postgres `sessions`, cookie handling
   unchanged — smallest change) or move to Supabase Auth and keep `users.id = auth.users.id`. RLS
   policies are written for the second case (`auth.uid()`), which is why `users.id` references
   `auth.users`.
5. **Environment on Vercel**: `DATABASE_URL` / `SUPABASE_URL`, `SUPABASE_SECRET_KEY` (server only),
   `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_ANON_KEY`, `APP_URL`, `ADMIN_EMAIL`.
   Never expose the secret key to the client.
6. **Build settings**: framework Next.js, build `npm run build`, install `npm ci`, Node 20+. Set the
   function region near the database.
7. **Seed production deliberately.** Do not run the demo seed. Create the first admin through a
   one-off script or SQL insert with a `scrypt` hash generated by `lib/password.ts`.
8. **Verify after deploy**: signed-out `/biz` redirects, QR endpoint returns 403 for a non-member,
   a sale awards points once, a voucher verifies once, `/admin/businesses` loads with the admin
   account, RLS blocks a direct anon query (e.g. `select * from ledger` with the publishable key
   returns zero rows).

## Environment variables

| Name | Required | Purpose |
| --- | --- | --- |
| `DATABASE_PATH` | no | SQLite file (default `./data/repeato.db`) |
| `APP_URL` | recommended | public origin, used in QR payloads and metadata |
| `NODE_ENV` | yes in prod | `production` enables the Secure cookie |
| `ADMIN_EMAIL`, `ADMIN_PASSWORD` | seed only | first admin |
| `DEMO_PASSWORD` | seed only | password for the demo accounts |
| `NEXT_PUBLIC_SUPABASE_*`, `SUPABASE_SECRET_KEY`, `SUPABASE_DB_URL` | Option B only | Postgres adapter / Supabase client |

## Operational checklist

- [ ] HTTPS in front, `NODE_ENV=production`
- [ ] `APP_URL` matches the public origin (QR codes encode it)
- [ ] Database on a persistent volume, with an online backup schedule
- [ ] Admin password rotated from the seed value
- [ ] Rate limiting moved to Redis if more than one instance
- [ ] Error monitoring (Sentry or equivalent) wired to the Next error boundary
- [ ] Logs retained for the audit table's retention period
- [ ] `npm test`, `npx playwright test`, `npm run build` green on the commit being deployed

## Not deployed by this build

No deployment was performed: no hosting credentials and no Supabase access token were available in
the build environment. Everything above is the verified, reproducible procedure, not a report of
something that happened.
